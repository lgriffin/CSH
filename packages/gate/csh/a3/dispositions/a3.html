1Background why this matters

These judgments were written by Claude, an agent, at the owner's request (issue #13, where the owner wrote "Make that call as an agent as this evolves for 13"). The owner may revise any of them. Like everything else in this component they are candidates: nothing is approved in any ledger, and the sheet says so in its header.

The gate turns one approved obligation into a disposition: allow, review, block or waived. Its requirements are the disposition table of the Authority tab (05, section 6). Its code is src/gate.ts, about 140 lines that the safety of every other run rests on. Its tests are test/gate.test.ts, repeated as a probe in test/gate.probe.ts so that each call to gate is a witness (A-49). Stage 15 wrote the table's rows as the sentences GATE-001 to GATE-007, wrote a model of the event Decide with a predicate for each row, and ran the three together for the first time.

How each practice is judged on its own terms: the table and its sentences by review, one row at a time; the tests by passing against gate.ts. Both pass. In CSH a sentence is cited, never translated, and a person writes the predicate, so the predicates and the model are where the rows meet each other.

4Root cause analysis each question as deep as the evidence goes

  1. Q1

    Why do 11 pairs of rows conflict when gate.ts passes every test?

    The rows' conditions overlap, and each pair that overlaps prescribes different dispositions. Stale crosses every verdict, and self-approved needing review crosses everything. gate.ts never conflicts because it checks in a fixed order (src/gate.ts:89, 90, 97, 107), so an earlier check settles any overlap. Neither the sentences nor the model state that order.

    Evidence: finding 5cb9cb853f53bb0c at stage first

    5 Whys to the root, below.
  2. Q2

    Why do two unit tests conflict with AllowSatisfied?

    GATE-006 allows every satisfied obligation. gate.ts sends a satisfied but stale one to review (src/gate.ts:97), and also one that is self-approved and needs review (src/gate.ts:107). The tests follow the code, so the rule is too wide and the tests are right.

    Evidence: finding 226609020dc65386 at stage first

    Evidence stops: the same missing order as Q1, seen from the tests.
  3. Q3

    Why is every row single-source?

    Only rules count towards this gap: the predicates and the model, which share one column (intent). The sentences are cited, never lifted, and the probe adds examples, not rules. Scenarios, the optional fourth practice of section 8, would also add examples, so they would not clear it. The rows are not unsupported: 17 witnesses cite them, and after C1 none contradicts them.

    Evidence stops: this is how the harness counts sources, and the lockout sheet keeps the same gaps.
  4. Q4

    Why does one test record no witness?

    "ignores candidate obligations, listing them" has no approved assessment, so the gate has nothing to decide and no Decide event to record. The probe calls gate without the probe on purpose (A-49). The test passes and counts in the Tests column (A-67).

    Evidence: “A case whose report has no approved assessment gives the” in test/gate.probe.ts

    Evidence stops: the case lies outside the event the probe records.
  5. Q5

    Should the GateSafety policy mark the intent critical?

    Critical changes one thing: an approved obligation of this intent that is unknown or stale blocks in enforcing mode instead of going to review (src/gate.ts:99). Nothing is approved, so it would change nothing that runs today. Choosing it means deciding how the gate treats its own unproven rules once they are approved, which is a decision about approval. No concrete reason to change it was found, so the policy is left as it is.

    Evidence: “if (a.critical && mode === "enforcing")” in src/gate.ts

    Evidence stops: a policy decision, left at its protective default.

4The 5 Whys asked until the answer is a process or a tool, never a person

  1. Why 1

    Why do the predicates conflict in pairs?

    Their triggers overlap, and on each overlap they demand different dispositions. For example, a satisfied, stale obligation meets AllowSatisfied (allow) and ReviewUnknown (review).

    Evidence: finding 5cb9cb853f53bb0c at stage first

  2. Why 2

    Why do their triggers overlap?

    Each predicate copies one row of the Authority tab's table. The table's conditions are not exclusive: "unknown or stale" includes stale obligations of every verdict, and "self-approved and needs-review" includes every verdict.

    Evidence: “WHEN an approved obligation is satisfied, THE GATE SHALL allow it.” in docs/requirements.md

  3. Why 3

    Why does gate.ts not conflict with itself?

    It reads the table as an ordered list. It checks conflicting (line 89), then violated (line 90), and reaches unknown or stale only through else (line 97). Self-approved review applies only while the row is still allow (line 107).

    Evidence: “if (a.selfApproved && a.needsReview && row.disposition === "allow")” in src/gate.ts

  4. Why 4

    Why did the sentences and the model not carry that order?

    They were transcribed faithfully from the table, row by row, and the table states no order. EARS has no rule for how two sentences combine. The model said so itself: where rows overlap, it says no more than the table (A-48).

    Evidence: “Where rows overlap the table does not say which” in spec/gate.csl.ts

  5. Why 5

    Why did nothing notice before stage 15?

    The unit tests pass against the code that holds the order, and each test checks one case, never two rows together. The table is reviewed one row at a time. Nothing read the rows side by side until CSH put them in one pool.

    Root cause, in a process: the table's order of precedence is recorded only in gate.ts's control flow, nowhere a reviewer reads as a requirement. Countermeasures C1 (requirement and model) and C2 (process).
